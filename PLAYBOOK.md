# PLAYBOOK

The current best way to do Trailmark's recurring work. For development only: `export-ignore` in `.gitattributes` keeps it out of the release zip and out of `SHA256SUMS`.

Run the lessons check below before each significant step. `CLAUDE.md` holds the user's rules and `dev/release-state.md` holds where the release stands. When this file disagrees with either one, they win and this file gets fixed.

## The lessons check

Run it before each of these: a design decision, a code change, a test run, a review brief, acting on a review finding, a push, a merge, a tag or a publish.

1. Get the rules. At the start of a session and after a compaction: `dev/lessons.sh` (every open rule). Before a later step: `dev/lessons.sh <words>`, with the step's topics (`commit`, `regex`, `review`). The steps in this file count too.
2. Write one line before acting, where the user can see it: `Lessons checked: <the rules that apply>`, or `Lessons checked: none apply`.
3. Follow each rule named. One that can't be followed goes to the user, with the reason, before the step.
4. After the step, report pass, fail or untested for each rule named.
5. Anything that broke, needed a redo, surprised you or drew a correction gets an entry in `LESSONS.md` before the next step. `dev/release-check.sh` fails on a broken entry (`dev/lessons.sh --check`).
6. A PR body ends with its `Lessons checked:` line, and a review brief tells the reviewer to run step 1.
7. A lesson seen twice, or clearly general, becomes a step here and is marked "promoted".

Limit: a session follows this by hand. Only the format in step 5 is checked by a tool.

## Constraints and known limits

- Windows, Git Bash: the Bash tool collapses `\\` in an inline command, a quoted heredoc included. No script goes in inline (`node -e`, a heredoc): every script, a scratch one and a small rewrite of one included, and every text for a command (a handoff, a PR body) is written to a file with the Write or Edit tool, whether or not a backslash is expected in it, and the file is run.
- Python writes cp1252 into a pipe: set `PYTHONIOENCODING=utf-8`.
- MSYS splits `PATH` at `:`, so a `C:/...` entry breaks: put `cygpath -u` paths in `PATH`. It also rewrites path arguments to Windows programs: call `wsl.exe` with `MSYS_NO_PATHCONV=1`. WSL's git can't read a worktree's Windows `gitdir`: clone for WSL from the main repository's `.git`.
- A `cd` in one Bash call moves the calls after it: use absolute paths or `git -C`, and `cd` only to the worktree's root.
- An inline command's text shows in the process list, so `ps | grep` probes match themselves: write probes to script files.
- This `gh` refuses output that holds escape sequences: a plain `gh api .../jobs/<id>/logs` exited 1 for each job with a log that it was tried on. Read a job's log with `gh run view --job <id> --log`, or pass `--allow-escape-sequences`.
- Windows gives back a killed process's file handles a moment after it exits: cleanup after a stop retries for a few seconds.
- PowerShell means `pwsh` (7), never `powershell.exe` (5.1), `gsudo` runs and `-File` scripts included.
- Node's `os.tmpdir()` uses `TEMP`/`TMP` on Windows, not `TMPDIR`. The user's `TMPDIR=E:\DevTemp` reaches tests only through `dev/release-check.sh`.
- Defender's MPLog is readable only by administrators. The user runs elevated scripts. Claude can't.
- Junction tests on Windows: libuv can fail with `EBUSY`/`EPERM` while the machine is busy (B8, `dev/release-state.md`). A deep temp path can also refuse init ("Windows, long paths").
- The writer runs under `node --permission`: it writes only in the memory folder and can't start programs. The launcher `scripts/trailmark.js` only reads.
- Codex: the memory folder is outside the workspace, so the sandbox refuses a checkpoint's first write and the skill asks for approval, unless the folder is a writable root (MANUAL.md section 3, the Codex README step 3).
- `main` requires the 9 jobs of `tests.yml`. Never add `paths-ignore`: a skipped workflow leaves the required jobs pending forever.
- Load-sensitive tests: the list lives under "Load-sensitive tests" in `dev/release-state.md`. Read it there, not from a copy.

## Do not attempt

- A plain `node --test`: it leaves `jbmem-*` folders in the system temp folder. Use `dev/release-check.sh --only`.
- Calling a failure "flaky", or adding a test to the load-sensitive list, without a reproduced cause.
- Tagging, publishing, force pushing or anything else that rewrites history, deleting branches or data (not temporary files or temporary folders the session itself made), changing the PC or its settings or those of the GitHub repo or the user's accounts, or downloading anything without the user's word. The same holds for a push, a PR or a merge, except under the deferred-item rule of `CLAUDE.md` "Conventions". A merge, tag or publish that needs the user's word is asked for by name, as its own question. Every merge, tag or publish is run as its own command.
- Attribution lines (`Co-Authored-By`, "Generated with") in commits, PRs, code or docs.

## Planning a change

1. Read `dev/release-state.md`, then the code the change touches. Notes go stale: check them against the code. A deferred item's claim about another program (git) is checked by running that program on the item's shapes, with a control that has a known answer and with the settings a repo can change, before a fix is designed; the fix then covers what was seen and no more.
2. Write the goal as a result you can check, and list what must not change.
3. Keep one purpose per change. A shared file in `plugins/trailmark` means the same edit in `plugins/trailmark-codex` (the `for f in` list in `tests.yml`).
4. During a frozen release, only a CONFIRMED regression in the last diff gets in. Everything else goes to the deferred list with its label, commit and repro.
5. Before a change inside a function is coded, or a sentence about its callers or about how far an input reaches is written: grep every caller of each function the change touches, in every file, and say for each what changes for it (its time budget, the size of the input it hands in, how it reads a new flag, return value or thrown reason). Grep the tests that call the function or count its work, and put their names in the `--only` pattern from the first run on. Before a change to what a failed lookup means, grep the tests for the calls and file modes involved as well, and run the whole test file on the system the change is for (WSL for Linux) before writing new tests.

## Writing code and docs

1. Match the file's existing style. Docs: no em or en dashes (use `--`), no tricolons, plain words.
2. A bug fix comes with a test that fails on the old code. Run it on the parent commit to prove that.
3. A file-system error path: list what Windows, Linux and macOS each return for it (ENOENT, ENOTDIR, EPERM, ...). This machine runs only Windows, so the test stubs the other systems' answer. A test that bounds the size of a text holding a path also runs with a TMPDIR 30 characters longer: CI's temp paths are longer than `E:\DevTemp`.
4. Wording edits across several files go through a script of exact old/new pairs that asserts each old text occurs once before it writes. Old text with backslashes or `\n` in it (code, tests) doesn't go in such a script: use the Edit tool on one copy and copy the file to the other, or swap a block between two plain markers from a text file. New code or tests never go in through an inline command either, a heredoc included: the Edit or Write tool. The `Lessons checked:` line before an edit names the tool the edit goes through.
5. Before handing over a script or file, read it for destructive or malicious operations, and say what you found.
6. After fixing a pattern, search the whole repo for that pattern before the first review.
7. A condition that skips a block, or code moved out of one: list each thing the block does in each case and ask whether the condition is about that thing. A value read before a lock can be older than the state under it: try the other order.
8. A new limit or refusal on a class matched by a pattern (a key's last letters, a name's shape): before it is written, list what real tools and users write in that class, starting with the sections where the user picks the key's name (`alias`, `pretty`), and run those values through it. A check on a key's value in a file format (a workflow's YAML) also lists each way the format can write that key (a plain key, a list item's first key, a flow mapping, a quoted or escaped key, a space before the colon), gives each a case, and refuses any line that names the key in a form it does not read.
9. A key that decides "already checked" stands for exactly one thing. Test both ways it can be wrong: two things under one key (one goes unchecked), and one thing under many keys (it is checked once for each, and links can make thousands).
10. In `dev/release-state.md`, point at another section by its name ("section RS-A-foldkeys"), never by its place ("top section", "second section", "above"): each new section moves every place.
11. Before fixing a reviewer's example, write down its class and say for each member whether the fix and the test cover it. For a table keyed by text from a repo (a Map, a Set, a tree) the members are: the same name under another parent and at another depth, in another case, with spaces at its ends (each on a system where such a name reaches the table), in another Unicode form, a number written two ways, and a name every object has (`__proto__`, `constructor`). Its mutation list starts with the swaps of the table (for a plain object, for one shared by all and for one shared by each depth), before the changes of its members. The test's comment says which members it holds; a change outside them is its stated margin.
12. A sentence in a doc or a comment about what another program does not do names the command that was run and what it did ("`git add` doesn't write such a path"), not the program as a whole ("git's own commands don't"). A comment that lists several commands says with which setup they were tried (a full index, a sparse one). The same holds for what the code does: a sentence names the shape that was run, or the neighbour shapes are run first, and "never" or "always" gives way to the cases tried. What git does at a path is written from a run of git at that path, with its version, in a test's expected answer too; until then it is HYPOTHESIZED, in the notes as well. A sentence that states a behavior gets a test or a probe named in the notes in the same batch.
13. A "tried" in a doc or a comment names each value it was tried at, or a range of which every value was run. The notes name the probe output that holds them. Where the result changes between two values that were run, the sentence says what the values between them did, or that they were not tried.
14. When a batch fixes a wording fault or logs a rule about wording, every sentence the batch adds or moves, in docs, comments and notes, is read against that fault and that rule before the commit, not only the place a reviewer named.
15. A count or a list in the notes, a comment or a test's expected value comes from a run that printed it, not from adding up by hand: a script over the test's own lines, which the notes name; a counter in the code, or the two sides of a boundary tried; `git diff --numstat` for a diff's changed lines; the "N probes" line of a list's last whole run for where a partial run starts. A comment at a count says what is counted and whose calls. An expected count is written, or changed after a surprise, only once the callers that do the counted work were read. A sentence that sums up several reports or failures ("each was caught", "every answer was X") is read against every item it covers, in the report or the kept output, before the commit, and names the exceptions.
16. Before a new name goes into existing code (a `const` in a test, a variable in a script), search the file for it. After an edit to a test file, `node --check <file>` runs before any test run.
17. A sentence that states an exception, or that changes what a model does (a skill, an instruction file), names its scope and what it is an exception to. Before it goes in it is read against every rule of its paragraph and every case its words reach, not only the case it was written for. A test that pins its exact text proves the text, not the behavior.
18. A new reason to keep git out in `farGitConfig` switches where `repoRoot` takes the root from. Before the first push the root is compared with the parent commit's: in a fresh process with both sets of scripts, on Windows and in WSL with the same probe script, for shapes where git works and for shapes where git fails, each shape plain and with an older reason to keep git out (a config that includes a share), and on Windows also from a session folder of 300 characters. The tests assert `localRepoRoot` next to each new refusal.

## Testing

1. New and changed tests: `dev/release-check.sh --only '<name pattern>'` (it runs both copies).
2. Then `dev/release-check.sh --sums --quick`. A doc edit after `--sums` needs `--sums --quick` again.
3. Leave the full suites to CI (three systems, three Node versions).
4. A failure: read the kept TAP output under `<temp>/trailmark-release-check/<run>` first, and copy the failed tests' lines into the notes folder at once. Compare its sign with the load-sensitive list. A sign not on the list is a new failure.
5. Intermittent failure: keep every run's output, log CPU, rerun with `--only` several times, and compare with the parent commit, alternating which runs first.
6. Report each item as pass, fail or untested, with what the test showed and what it didn't.
7. A test that skips on a time sign: its control repeats the exact call, covers every step whose time can give the sign, and takes its bounds from the product's budget. Prefer the product's own report of each step's time left and spent (a `JBMEM_SHOW_*` stderr line that only reports) over times measured from outside, which grow with load whatever the cause. Before it ships, run a forced non-time fault (must fail) at rest and under busy loops, and each step forced slow (must skip).
8. Read why each new test fails on the old code: a failure for another reason proves nothing. Remove each part of a fix alone and check that a test fails. An assertion that something didn't happen gets its own forced fault, in each case that makes it: a case that could not have made the thing happen doesn't claim it. A comment that names a class or a family gets a case for each member, taken from where the program lists them. Where the members carry a number, the cases are a loop, the comment gives its range, and the mutation list changes the pattern from the second member up and at each digit count. Before a case is taken out or loosened, write down each thing it proves at each layer it runs through (the caller, then the function), and keep a case for each; for a table, the mutation list has one change for each key at each layer. Where several rules or several places give the same answer, a case's input is one where only the one under test can give it (a clock that is short at one ask only, or a count of what was touched after the limit was hit, asserted in each case).
9. A search, a scan or a probe that finds nothing proves nothing until the input is shown to exist and the search to work (a download that failed, a grep that errored): it runs beside a control with a known answer, such as the same call on a job of the same run that has a log. Any result counts only once its run shows that it reached what it was built for: a probe prints the reason it got and is read against the reason it was built for, a script that reads a test run passes `--test-reporter=tap` and prints the run's pass and fail counts, a partial run's output is read for the names expected, and equal times on the parent and on the fix read as "did not run".
10. A validator, or a decision made from a text by a pattern, a table or a compare, is tested with the texts near each valid one. Where the decision is made once for each item of a list, a loop makes the near texts and the mutation list loosens each compare each way. The full case list is in `dev/testing-cases.md`, which also covers a test of a limit, a stand-in for a program, a stub on a shared function, a clock handed to the code, a test's comment, and a note about a test or about what a fix covers. Read it before writing or changing any of those.
11. A limit on a count or on counted work: before it is written down, time the dearest thing one counted item can be (a folder to list, not a file's name; a disk lookup, not text) at the limit itself, on Windows and Linux. The weights of a counted limit come from units per second measured on the cheapest and on the dearest kind of step with an unlimited copy, set so that the two rates are within a small factor; the honest inputs are sized at the longest path and depth a real repo can have, and the margin is stated. A look at the time once in N steps is written only after one step was timed on the slowest disk here (a Windows drive in WSL), and a step that asks the disk gets a look each time.
12. A new test's calls with a real-time budget: give each a third of its budget and run the test once. A failure names an assertion tied to the machine's speed: stand the clock still for that call, or stand in for git. A case that needs real git to be stopped by a short timeout accepts git finishing too, and its strict form uses a stand-in.
13. Before a time for a limit goes in a shipped text: list every step between reading an input and the first counted line, and for each step every input its time grows with (a text, the folder it is joined to, the path a disk call names). Give the search for the slowest input one shape for each, at its largest size (text work before a walk was missed twice, the length of a path once), and read the time at the last size the limit lets through. The cause of a slow path is written from a profile or a probe, not from what the fix changes. Before slow code is bounded, the slow input is profiled (`node --cpu-prof`, top functions by self time) and most of its time is accounted for by name; after the fix the slowest accepted input is profiled again, and what is left must be what the limit counts.
14. A time in a shipped text comes from at least three runs, with the first run after the files are made told apart from the rest, and from at least two shapes that differ in what could set it (depth, size, name length, the folder the process works in, a fresh process). Its probe lists what it held fixed. A time claimed for a hook or for a refusal is measured through what a hook runs first as well as through the changed function (the hook started as a process, `trailmark.js --hook <name>` with a payload on stdin; `repoRoot` as well as the check), on the parent and on the fix, and the sentence names what was measured. A slow reading that does not come back is written in `dev/release-state.md` as unexplained, with what was ruled out: repeat the same series of runs with the processor use of every process sampled each second.
15. A shipped text gives a time for a named shape and never a ranking ("the slowest left"). When a second review finds a slower shape for the same limit, add no further term to the count: write down what the shapes share and cap that input (three rounds of RS-A-worktreeslinks each beat the last time, the last two with paths of thousands of characters). A test of a term runs at the size that drew the fix, not at the size its fixture is easy to make.
16. A mutation list starts only after the changed test passed once alone with the fix in place and no mutation applied (`--only`, its PASS line read) and after the other system's run: a test or a part of one that this machine skips is run where it isn't (WSL for links) before its result or its mutations count, and a test edit runs the whole list again. A probe counts as caught only when its result line has a count for the tests it ran ("N failed of 2") and its edit is shown to have applied at the entry or line it names. Any other line is "no result": the probe is run again, and it holds the batch if it stays (one that ends in 0 s did not run). A probe's label comes from that probe's own result, and names the systems that catch it ("Linux only") only after a run on each system printed its result; the record says which system each result came from. While the list or any other run is going, the files it reads or changes are not changed, and the files it changes are not read either (wait for the run to end, and for a mutation run to print that it restored its files, or run a copy), and a run that overlapped an edit doesn't count. After a change that loosens an assertion the whole list runs again.
17. A probe removes what it made in a `finally` that prints what is left (`removed false` with the path), so that a failed cleanup is a line in the output and not a missing one. A chain of folders is removed from the deepest up with `rmdir`. A folder left behind is removed by its literal path, by a script that refuses any other; in a command, each variable of a path to delete is guarded (`${B:?}`).
18. A change to what a hook does, or to what a skill tells the model, is also run in a real host session before its PR: Claude Code, or Codex for the Codex copy, in a scratch repo set up for Trailmark, with the changed copy loaded. The notes say how the copy was loaded and what the session showed (the handoff in the model's context, a checkpoint written). A test that runs `trailmark.js --hook <name>` with a payload can pass while the hook does nothing in a session. A run that needs what only the user can do (a sign-in) is asked for; until it is made, the notes and the PR body say "untested in a host", and the PR is not set to auto-merge until the user decides.
19. A function that folds, normalizes, parses or encodes text from outside (a path, a key, a payload) gets an invariant test beside its examples: a rule that holds for every input, such as folding twice gives what folding once gives, reading a written value gives it back, or the fast path agrees with a plain slow version. The inputs come from a loop over a stated alphabet and length range, so a failure can be run again; the test's comment gives both. No property-test library: adding one is a download, which is asked.
20. A rewrite that must keep behavior runs the old and the new code over the same inputs in one probe and prints every difference. Each intended difference is listed in the notes with its reason; any other is a bug. The root compare of "Writing" step 18 and RS-T-ziptz's compare of `--zip` with `TZ=UTC git archive` are this kind of check.
21. A failing test is not made to pass by a sleep, a rerun in place of a cause (step 5 reruns to find one), a new skip or a looser bound, unless its cause is proven and the change answers that cause. A skip on a time sign built as step 7 says answers its cause in this sense, as does a skip on a system where the test can't run (a stand-in for git on Windows). Three reruns of a CI job that hung are evidence for the user, not a pass: each must pass, and the hang stays recorded.

## Committing

1. A commit goes in a later message than the edits it depends on, after they succeeded. A commit script that follows an edit of the notes also looks for a text only that edit adds.
2. Never chain a commit after a check piped into `tail` or `head`: read the check's summary, then commit.
3. Before a batch's commit, each sentence it adds (a comment, a note, the commit message) is read once against the line or the run that makes it true. One that names a commit is read at that commit (`git show <commit>:<file>`).
4. A scan that guards a commit, a push or a send prints a count from what it read, and is run once on a text known to hold what it looks for. An exit code that is neither "found" nor "not found" stops the step: `grep -P '[\x{2013}\x{2014}]'` in Git Bash on this machine exits 2 ("character value in \x{} or \o{} is too large"), and `||` or `if` reads that as nothing found.
5. An edit's old and new text end on a visible character, at the end of a line. Before the check that guards a commit starts, the diff of code and tests is read line by line, not only counted.
6. A merge whose conflict is in a file of entries (`LESSONS.md`, the sections of `dev/release-state.md`), resolved by keeping both sides: git keeps a line both sides end with (`- Status: open`) once, outside the block. Before the merge commit, run `dev/lessons.sh --check` and compare the entry or section titles with the union of both parents'.
7. A commit made in a session (not a merge commit GitHub makes) ends its message with a `Verified:` line that names what ran on its tree and passed (`--only '<pattern>'`, `--sums --quick`, a review round, a probe named in the notes), or `Verified: none` with the reason (`Verified: none, notes only`). `git log --grep='Verified: none'` then finds the commits nothing checked.

## Pushing and CI

1. CI is read as the jobs listed on the pushed head, counted against the 9 required names once the list has settled, not as a run's status and not from a short list. A red run with no failed job means reading GitHub's incident feed before suspecting the code. With 0 checks on a pushed head, read the runs list (`gh api repos/<repo>/actions/runs?per_page=3`) and look again after other work, not in a loop.
2. After a push, a merge command (auto-merge too) goes in a later step, and only once `gh pr view <n> --json headRefOid,statusCheckRollup` shows the pushed head with its 9 jobs listed, pending or passed. If a merge does go in ungated, say so at once, watch the run on `main` for that merge commit, and fix forward on a failure.
3. A new check that can fail CI or stop a commit (a step in `tests.yml`, a rule in `dev/release-check.sh` or in `dev/lessons.sh --check`) reports only for at least one PR before it can fail anything: `continue-on-error: true`, or a warning in place of a failure, as the watchdog test step in `tests.yml` does. What it would have failed is read before it is made to fail.

## Reviewing

1. One reviewer per row the diff touches (model table in `CLAUDE.md`), on `git diff <last reviewed>..HEAD` only.
2. The brief gives the goal, the files, what earlier rounds fixed, what the report holds (each finding first with its label and repro, then what was tried and found clean, and nothing that restates the diff), its own clone (detached at the head under review, with no remote) and its own empty temp folder outside that clone, and where the report lands (the owning branch's next batch push). It also says to use `pwsh`, never `powershell.exe`, and sets `TMPDIR=E:\DevTemp` itself when kept output should land on the Dev Drive (a subagent's Bash has TMPDIR on C:). It gives the test command as one line with `TMPDIR`, `TEMP` and `TMP` set to that temp folder in front of it, and says to run a test no other way; after the round, also one whose reviewer died, the owner lists `jbmem-*` in the temp folders and removes each clone and temp folder by its literal path.
3. Tell the reviewer to read `PLAYBOOK.md` and `LESSONS.md` first.
4. Reproduce every finding before acting on it, also one labeled CONFIRMED, with the reviewer's own shape and numbers first and varied after. When a reviewer's number differs from the notes, both shapes run in one process in the same minute, a probe changes one thing at a time, and the cause is named only once one run shows both numbers.
5. Gather a round's findings plus the scanner and Copilot comments on that head, fix them in one push, then review that push once. While another session runs a review round on the branch, pushes are held for that round's batch unless the user says otherwise.
6. When a second round finds about as many points of the same kind as the round before, the fault is in the method, not in the lines: stop adding one more instance and change the method. A time gets a cap on its input in place of a further term ("Testing" step 15), a test changes shape and gets no further cases of the old kind, a rule is cut back. A rule that lets a session act without asking gives its scope, the one condition that must hold and a default for everything else (it is asked).
7. A change that edits a check that judges it (`tests.yml`, `dev/release-check.sh`, `dev/lessons.sh`, `.github/tap-annotate.js`, or a test's assertion made looser) names each such check in its PR body and its review brief. The reviewer also runs the base branch's version of that check on the PR's head where it can run, and reads each loosened assertion beside the parent's.
8. A fix whose own test or check still fails after three attempts at that same failure goes to the user with the three attempts and what each showed, before a fourth attempt, with auto-merge off. Review rounds that each find something new are not counted here: the stop rule of `CLAUDE.md` "Reviews" covers them.

## Releasing

Follow the current version's "Release checklist" in `dev/release-state.md`. Older versions keep their own checklists there, with their own version numbers and paths: don't follow those. Then:

1. `dev/release-check.sh --zip <dir>` from a clean tree at the release commit. Record the commit and the zip's sha256 in `dev/release-state.md`.
2. Check the zip holds the change: unzip it and search for a string only the change adds. Check that `CLAUDE.md`, `PLAYBOOK.md`, `LESSONS.md` and `dev/` are absent.
3. After publishing, download the assets back and run `sha256sum -c`.
4. `.github/workflows/release-draft.yml` puts the zip of a version with no tag in a draft release after each push to `main`, replacing an earlier push's draft. Steps 1 and 2 can use the draft's zip instead of a local build. Publishing the draft makes the tag, and that stays the user's word. The job doesn't wait for `tests.yml`, so check that its jobs passed on that commit before publishing. A draft with the job's hidden mark in its notes is replaced by the next push, edited notes included. A draft without the mark stops the job with nothing changed.
5. A CHANGELOG line is written from the merged code. A PR description or a batch's note is a list of what to cover, not text to copy: a line that names a reason, a number, a file or a copy is read against the code or against `git diff <last tag>..HEAD` for that thing before the review, and the list of changes in behavior is taken from that diff (new constants, the environment git gets, the rows of MANUAL.md's reason table).

## At each milestone

1. Sweep every project session, branch, worktree and open PR: unpushed work, untracked reports, pending asks.
2. One session owns each step that starts sessions, pushes or merges. A side session asks only its starter about such a step, not the user, and anyone acting on a yes first checks `list_sessions {"linked": true}` for the same step already done.
3. Update `dev/release-state.md` so the next session can start from it.
4. Log any mistake, redo or surprise in `LESSONS.md` right away. A lesson seen twice, or clearly general, becomes a step here and is marked "promoted".
5. A session that ends on an error (a request timeout, say) is resumed at once by the session that started it: check that its branch and worktree are intact, then send it the next step. A review whose report never arrived is run again. Sessions commit before starting a long review, so a stop can lose only that review.
6. When one session changes another session's PR (auto-merge, a merge), it tells that session in the same step.
7. A time written in the notes, a handoff or a report is one that a command printed (`date +%H:%M:%S` in front of the command it belongs to). A time that was not printed is not written.
8. Nothing wakes a session when a PR merges, and sessions don't poll CI. A session never promises to report on something that can't wake it. Its closing line says who acts next and what triggers that.
