# Testing cases

The case list for `PLAYBOOK.md`, "Testing", step 10. For development only: `dev/` stays out of the release zip. Read it before writing or changing a test of a validator, of a limit, or of a decision made from a text by a pattern, a table or a compare. Read it too before writing or changing a stand-in for a program, a stub on a shared function, a clock handed to the code, a test's comment, or a note about a test or about what a fix covers.

A validator's negative cases include inputs one small edit away from valid, what happens to the data after a line it doesn't recognize, and state left open when the input ends. A test of a limit has one item at exactly the limit and one at exactly the limit plus one (two folders side by side, such as `a` and `bb`: a folder inside another is at least two characters longer), and asserts the length of one of them. A decision made from a text by a pattern or a table sits in a function the test asks directly, with every text near each valid one (more, a line or a space at either end; other capitals; cut short; the same value under another key) and each valid one asked twice; cases with the real tool stay for the path a value takes to that function. This holds for a plain compare too: where the decision is made once for each item of a list, the near texts are made by a loop and not chosen (every text one change away at every place: a character left out, put in or changed, two neighbors swapped, over a stated set of characters, a changed character also in its wide form, and a letter with its accent in both Unicode forms, each way round), for the first, a middle and the last item and for each part compared, and the mutation list has each compare loosened each way (starts with and ends with in both directions, one character let differ, other capitals, NFC and NFKC as two probes, spaces around) and held for one item only. One case has a list longer than the other cases' lists, with the item at every place of it, and the mutation list has the decision made for the first N items only (N the other cases' length, and the long list's length less one). A stand-in for a program checks the question it gets (every argument) and answers from it as the program would, and the cases with the real program have one for each way the thing asked about can come to be (each word, each place a setting can come from). A stub on a shared function (`fs.lstatSync`) matches on the path from the test's own folder, not on a name alone, and a branch of it that changes what the rest of the test sees (a clock, a counter) sets a flag that the test asserts in each case. Every clock handed down gets a case where time passes after that clock was made and before its last read, and the mutation list has "does not run" for each clock, not only the first. A test's comment, and a note about the test, say what its cases try in the cases' own terms: a word for a class ("more after it") stands only over a loop that tries every member, with the loop's bounds given. A set or a range that a comment or a note names is held by an assert that walks it (each member named is among those tried): a floor on a count shows that a loop ran, not what it ran over. A note that says what a part of a fix does or does not cover, or that an input changes nothing, comes from a run with the other parts taken out and gives what that run answered; the limit that is left gets a case of its own.
